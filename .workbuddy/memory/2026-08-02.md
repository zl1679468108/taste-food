## PC 管理后台 Dashboard 统计超时修复（T312）

- **症状**：PC 后台 Dashboard 弹 "timeout of 10000ms exceeded" + "统计数据加载失败，请稍后重试"（截图：clipboard-2026-08-02T13-33-42）。
- **根因诊断**：
  1. `axios.create({ timeout: 10000 })` 全局 10s（`admin/src/utils/request.ts:269`）
  2. `GET /api/orders/stats/today` 在 Supabase 跨区网络下稳定 5~11s（curl 实测）
  3. 触发原因：`tf_orders` 只有单列 `idx_orders_shop_id` / `idx_orders_created_at`，无法覆盖 `WHERE shop_id=? AND created_at>=?` 的范围扫描
  4. Node 端还要把全量订单行拉到内存做 JS 聚合（`server/src/modules/order/order.service.ts:3604-3635`）
- **修复方案（已落地）**：
  1. 数据库层：新增复合索引 `(shop_id, created_at)` 与 `(shop_id, status, created_at)`（`docs/database-init.sql` + `docs/migrations/v30-orders-stats-perf.sql`）
  2. RPC 层：新增 `get_today_stats(p_shop_id)` / `get_daily_stats(p_shop_id, p_start_date, p_end_date)` 两个 SECURITY DEFINER RPC，SQL 端用 COUNT FILTER + SUM FILTER 一次返回；`get_today_stats` 兼容老的 `tf_daily_stats` 预聚合
  3. 后端层：`order.service.ts` 优先调 RPC，RPC 缺失时 fallback 到原 SELECT 逻辑（防御性兼容）
  4. 前端层：`admin/src/services/order.ts` 给 `getOrderStats` / `getDailyStats` 单独配 `timeout: 30000`，避免 Supabase 跨区冷启抖动
- **实测耗时**（RPC 缺失、回退路径）：stats/today 11.6s、stats/daily 11.1s（仍然超时，但前端 30s 兜底不会触发 10s timeout 错误）
- **需用户执行**：`docs/migrations/pending-v29-v30-apply.sql`（合并 v29 + v30）在 Supabase SQL Editor 跑一次。已生成合并文件，v29 是 T308 语音播报配置列的最终落库，v30 是上轮 stats 性能修复的补刀。
- **文档同步**：`docs/tasks.md` 新增 T312.1（远端执行）/ T312.2（验证耗时回归）

## T308 语音播报配置保存失败（schema 缓存问题）
- **症状**：商家点「保存」/「恢复默认」时弹 "更新语音播报配置失败: Could not find the 'voice_alert_config' column of 'tf_shops' in the schema cache"（截图：clipboard-2026-08-02T14-38-37）。前端「已恢复为系统默认设置」是本地状态切换，与服务端持久化解耦，所以恢复默认 toast 仍会成功。
- **根因**：`docs/migrations/v29-shop-voice-alert-config.sql` 一直没在 Supabase 远端执行，`tf_shops.voice_alert_config` 列物理不存在。PostgREST 把这条信息缓存在 schema cache，所以 PUT `/api/merchant/shops/:id/voice-alert-config` 的 `update({ voice_alert_config })` 直接 42703 报错。
- **解法**：把 v29 + v30 合并成 `docs/migrations/pending-v29-v30-apply.sql`，在 Supabase Dashboard SQL Editor 一次性跑完（两个迁移均幂等，可重跑）。
- **自检 SQL**：
  - `SELECT column_name FROM information_schema.columns WHERE table_schema='public' AND table_name='tf_shops' AND column_name='voice_alert_config';`
  - `SELECT proname FROM pg_proc WHERE proname IN ('get_today_stats','get_daily_stats');`
- **用户 22:42 在 Supabase SQL Editor 跑完 pending-v29-v30-apply.sql → 实测验证通过**：
  - `voice_alert_config` 列存在且可 select（原 42703 消除）
  - `get_today_stats` RPC 返回数据
  - round-trip 写/读/重置 null 全通过 → 商家「保存 / 恢复默认」PUT 现在能落库
- **v30 stats 稳态耗时**：warm 后 RPC 0.5s，但跨区冷启仍 10~11s 抖动（DNS+TCP+SSL，与 SQL 无关），前端 30s 兜底不会爆红。SQL 路径已生效。
- **教训**：PRD 标 ✅ 与数据库真实状态是两回事。今后任何 ALTER/CREATE 写完迁移 + 代码，必须立刻让用户跑迁移并回贴 schema 自检结果，再勾 PRD。
- **待用户验收**：去 PC 后台「语音播报」页点一次保存 → 应不再弹"更新语音播报配置失败"。

## 重要约定（本次修复沉淀）
- **Supabase 跨区冷启**：本地连 Supabase 远端首查有 5-11s 延迟（DNS+TCP+SSL+Auth），不能假设 < 1s。涉及 dashboard 这种聚合查询的 timeout 必须 ≥ 30s
- **stats 接口的防御性兼容**：迁移 SQL 跑与不跑都能用——后端先 RPC 后回退，索引 CREATE INDEX IF NOT EXISTS 幂等，RPC CREATE OR REPLACE FUNCTION 幂等
- **DNS 解不到 Supabase PG 直连**：`db.<ref>.supabase.co` 在国内 DNS 被污染，本地 pg 客户端无法直连。修改 Supabase schema 必须经 Supabase Dashboard SQL Editor 或 Management API（需 access_token）

## 堂食桌号残留显示修复
- 用户反馈：未扫码却显示「堂食桌号 1001」。
- 根因：`dine-context.ts` 的 `saveDineContext()` 将桌号持久化到 `tf_dine_context`（Taro storage），之后每次进入菜单页 `loadDineContext()` 都会从存储读取并展示，无过期机制。开发/测试阶段扫一次后永久残留。
