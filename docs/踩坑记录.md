## 2026-08-05 砍死表漏查数据库 RPC 依赖，导致生产下单报错

- **场景**：表需求审查判定 `tf_refresh_tokens`（Legacy 死表）与 `tf_item_sales`（销量明细，已被 `tf_menu_items.monthly_sales` 覆盖）为伪需求，经 Management API 对生产库执行 `DROP TABLE`（v38 迁移）删除。
- **现象**：删除后生产环境**下单走降级路径**（`atomic_create_order` RPC 失败 → `createOrderLegacyFallback`，见 `server/src/modules/order/order.service.ts:1413`），错误日志增多、原子性变差；若降级也失败则直接下单失败。
- **根因（两层）**：
  1. **只查了应用代码，没查数据库函数**：`order.service.ts:1384` 下单核心调用 `atomic_create_order` RPC，而该 RPC 函数体内部有 `INSERT INTO tf_item_sales`（`docs/database-init.sql`）。`tf_item_sales` 在**应用层零引用**，但在**数据库层被 RPC 写入**——"零应用引用 ≠ 死表"。
  2. **双重载残留**：生产库存在两个 `atomic_create_order` 重载（16 参旧版[早期迁移遗留，含坏 INSERT] + 17 参版[server 实际调用]）。`CREATE OR REPLACE` 只覆盖 17 参签名，旧 16 参版仍在且仍写死表。
- **修复**：
  - 生产库：两个 RPC（`atomic_create_order` / `atomic_increment_menu_sales`）去掉 `tf_item_sales` 写入，只保留 `tf_menu_items.monthly_sales` 更新；
  - 生产库：`DROP FUNCTION` 清掉 16 参旧重载；
  - `docs/database-init.sql` 同步删除两张死表的 `CREATE` 块 + 两个函数里的 `INSERT`（三位一体）；
  - 用 `SELECT pg_get_functiondef(oid) FROM pg_proc WHERE proname IN (...)` 验证无残留引用。
- **教训 / 防呆 checklist（砍任何表前必做）**：
  1. 不要只 Grep 应用代码。**必须查数据库内对象对目标表的依赖**：
     ```sql
     -- 查 RPC / 函数 / 触发器体是否引用某表（prosrc 是函数体源码）
     SELECT proname, pg_get_functiondef(oid) AS def
     FROM pg_proc WHERE prosrc ILIKE '%tf_target_table%';
     -- 查视图
     SELECT viewname FROM pg_views WHERE definition ILIKE '%tf_target_table%';
     -- 查外键（子表引用目标表）
     SELECT tc.table_name, kcu.column_name
     FROM information_schema.table_constraints tc
     JOIN information_schema.key_column_usage kcu ON tc.constraint_name = kcu.constraint_name
     WHERE tc.constraint_type = 'FOREIGN KEY' AND tc.table_schema = 'public'
       AND ccu.table_name = 'tf_target_table';
     ```
  2. `CREATE OR REPLACE FUNCTION` 只覆盖**相同参数签名的重载**，注意清理历史残留重载（否则旧重载仍引用死表）。
  3. 删除后回查 `pg_proc.prosrc` 确认零引用，再宣布"安全"。
  4. 砍表要同步 `docs/database-init.sql`（三位一体），否则初始化脚本会建回被砍的表。
