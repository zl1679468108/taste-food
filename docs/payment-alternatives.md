## 一、背景

本项目为个人主体微信小程序（线下小餐饮扫码点餐）。核心问题：**不走官方微信支付（个体工商户 / 企业资质）的前提下，是否存在其他可行的收款方案。**

## 二、硬约束（不可逾越）

- 微信支付商户号要求**个体工商户或企业**资质，个人主体无法开通。
- 因此 `wx.requestPayment` 在小程序内**无法调用**（无商户号绑定直接报错）。
- 结论：**个人主体 + 小程序内真实在线收款，在微信平台规则下无解。** 任何"在小程序内拉起微信 / 支付宝实时收款"的路径均为死路。

## 三、项目现状（已实现）

`server/src/modules/payment/providers/payment-provider.ts` 已抽象三层支付渠道：

| 渠道 | 现状 | 说明 |
|------|------|------|
| `sandbox` | 开发 / 演示默认 | 立即成功（`mock:true`），当前默认通道 |
| `wechat` | 占位 | 官方微信支付，配置齐全前返回明确错误，待企业商户凭证（T43） |
| `third_party` | 未实现 | 注释明确"非免费且合规风险高"，保持暂缓 |

## 四、候选方案对比

| # | 方案 | 可行性 | 合规 / 拒审风险 | 说明 |
|---|------|--------|----------------|------|
| 1 | 到店支付 / 货到付款 | ✅ 推荐 | 合规、0 成本 | 小程序只点单，到店现金 / 商家扫码付。`sandbox` 即其数字版，建议升级为正式"柜台支付"语义 |
| 2 | H5 网页 + 商家收款码 | ⚠️ 有拒审风险 | 高风险（见第五节） | 脱离小程序审核是"表面成立"，关联引流即拒审 |
| 3 | 第三方聚合支付（PayJS / 虎皮椒等） | ❌ 不推荐 | 二清违规 + 调不起 `requestPayment` | 资金先进服务方再结算 = 二清；小程序内跳 H5 收银台违规；微信常态化打击封号 |
| 4 | 升级资质（个体户 / 企业） | ✅ 唯一合规真收款 | 无 | 用户已排除 → 2026-08-02 起主动了解线上注册步骤，决策转向考虑该路线；成本极低（几分钟、几乎免费），是 `wechat` provider 既定归宿 |

## 五、H5 网页 + 收款码 的拒审风险（重点澄清）

"网页不受小程序审核约束"这一判断**过于乐观**，必须加前提条件：

- 独立 H5 网页本身确实不受《小程序运营规范》审核约束；但若作为"小程序之外的补充渠道"并与小程序产生**关联引流**，则风险立即触发：
  - 若小程序内出现任何入口 / 链接 / 文案引导用户到该 H5 收款 → 违反运营规范"不得诱导用户到小程序外进行支付"，**提交审核会被拒 / 上线后被下架**。
  - 即便 H5 完全独立、仅靠线下桌贴二维码获客（用户线下扫码打开 H5 付款），**小程序内仍不得提及该 H5 或暗示此支付路径**。
- 此外，微信 / 支付宝**个人收款码**用于经营收款存在额度限制与风控（个人码不得用于经营性收款）。
- 结论：该方案"安全"的前提是 **H5 与小程序完全隔离（不从小程序引流）**，仅靠线下物料获客；一旦关联即拒审。不能因"网页形式"放松合规判断。

## 六、落地建议

- **demo / 试运营**：继续 `sandbox`，但建议语义化为"到店支付"——保留 `pending_payment` 或新增 `pending_counter`，前端按钮改"提交订单 · 到店付款"，商家端加"确认收款"。将来接真支付只需替换 provider。
- **真要收款又不愿办资质**：若走 H5 + 收款码，必须确保与小程序**零关联引流**，仅线下物料获客，并接受个人码经营风控。
