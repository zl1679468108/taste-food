# taste_food_order 三端代码审查报告

> 本报告基于对 `server/`（NestJS 后端）、`client/`（Taro 微信小程序）、`admin/`（Ant Design Pro + UMI 管理后台）三个端的系统性审查，从【功能逻辑缺陷】【代码写法问题/优化】【交互统一性】三个维度梳理。
>
> 问题分级：
> - 🔴 **严重缺陷**：影响功能正确性、数据一致性、安全性
> - 🟠 **一般缺陷**：边界问题、健壮性、可维护性
> - 🟡 **代码优化**：重复代码、性能、TypeScript 严谨性
> - 🟣 **交互不一致**：跨端/跨页面风格不统一

---

## 一、整体概览

| 端 | 严重 | 一般 | 优化 | 不一致 | 关键风险点 |
|----|------|------|------|--------|-----------|
| server | 13 | 30 | 22 | 15 | 事务原子性、WebSocket 多租户、AuthGuard 未全局 |
| client | 20 | 42 | 50 | 22 | 微信支付未调起、401 未联动 store、规格 key 冲突 |
| admin | 8 | 22 | 14 | 12 | Promotion 缺规则字段、登录不刷新 access、订单取消缺失 |

**最紧急 Top 10**（影响生产可用性）：

1. 🔴 **client S3**：`payOrder` 未调起 `Taro.requestPayment`，等于"免费下单"
2. 🔴 **client S1**：401 处理未联动 `authStore.logout()`，socket 持旧 token 重连
3. 🔴 **client S2**：order-detail 用 `navigateTo` 跳 tabBar 页面必失败
4. 🔴 **client S10**：提交订单前端传 price 字段，存在价格篡改风险
5. 🔴 **admin S5**：Promotion 表单缺 rule 字段，所有营销活动规则为空、全部失效
6. 🔴 **admin S3**：管理后台缺"取消订单/退款"操作，商家无法处理已支付订单
7. 🔴 **admin S8**：登录成功未 `setInitialState`，access 守卫失效需刷新页面
8. 🔴 **server S1/S2/S3**：订单状态变更、取消、支付三处都非事务原子，存在脏数据风险
9. 🔴 **server S6**：WebSocket 按 admin/rider 全局房间广播，多租户隔离缺失
10. 🔴 **server S10**：AuthGuard 未注册为全局守卫，多处 GET 接口完全公开

### 2.2 一般缺陷（重点摘录）

- **G1** `order.service.ts:259-263`：首单优惠判断存在 race condition（两个并发请求都读到 total=0）
- **G2** `order.service.ts:225-240`：起送价校验只对 DELIVERY 生效，自取/堂食漏校
- **G3** `menu.service.ts:303`：`ilike` 搜索未转义 `%`/`_`，搜索 `100%` 会误匹配
- **G4/G5** `menu.service.ts:374-396, 465-485`：`createMenuItem`/`updateMenuItem` 忽略 `specGroupIds`，规格关联永远写空
- **G7** `order.service.ts:139, 165`：`fetchItems` 错误时静默返回空数组，订单详情会显示无 items
- **G8** `roles.guard.ts:32` 与 `promotion.controller.ts`：`@Roles('admin')` 字符串与 `UserRole.ADMIN` 枚举混用
- **G11** `order.service.ts:617-630`：退款记录更新失败仅 warn，payments 与 orders 状态可能不一致
- **G19/G20/G21** `notification.service.ts`：access_token 无缓存、orderId 截断导致跳转失效、fetch 无超时
- **G22** `supabase.client.ts:75-138`：健康检查失败后同步 `getSupabaseClient()` 一直返回 null
- **G25** 所有 service：`toRecord(row: any)` 类型不安全，TS 不校验字段拼写
- **G27** `order.controller.ts:193-207`：reorder 不复制 `contactName/contactPhone`，外送订单丢失联系方式
- **G29** `order.controller.ts:171-182`：`cancelOrder` 未限制 rider 角色，骑手可取消他人订单

### 2.3 代码优化建议

- **O1** `DEFAULT_SHOP_ID` 硬编码散落 6 处 → 抽到 `common/constants/shop.ts`
- **O2/O3** `isProduction`/`assertMemoryFallbackAllowed` 重复定义 → 抽 `common/utils/env.ts`
- **O4** 所有 service 的 `toRecord/toResponse` → 抽 `BaseMapper<Row, Record, ResponseDto>` 抽象类
- **O5** 日期格式化手工拼接重复 3 次 → 改用 `dayjs.format('YYYY-MM-DD')`
- **O10** 模块级 `memoryUsers`/`memoryOrders` Map → 移到 class 实例属性
- **O13** `main.ts` 未挂载 Swagger → 引入 `@nestjs/swagger`，dev 环境挂 `/api/docs`
- **O14/O15** 全局 ValidationPipe 用 `app.useGlobalPipes` 运行时配置 → 改 `APP_PIPE` provider；自定义 `common/pipes/validation.pipe.ts` 实际未使用，应删除
- **O22** `order.gateway.ts` 无心跳配置 → 加 `pingInterval: 10000, pingTimeout: 5000`

### 2.4 交互不一致

- **I1** 错误响应 `code` 字段语义与成功响应冲突
- **I2** 所有 POST 创建接口都返回 200，未加 `@HttpCode(201)`（违反 AGENTS.md 规范）
- **I3** `OrderQueryDto` 同时混用 snake_case（`user_id/shop_id`）和 camelCase（`page/pageSize`）
- **I5** 角色 `@Roles('admin')` 字符串与 `@Roles(UserRole.ADMIN)` 枚举混用

- **I8** GET 接口鉴权策略不一致（menu/shop 无 AuthGuard，order 有）
- **I13** PaymentController 与 OrderController 共用 `@Controller('orders')` 前缀
- **I15** `notification.service.ts:159` 后端做分→元转换，违反"金额存储为整数（分），前端展示转换"规范

## 五、跨端共性问题

### 5.1 代码重复，应抽取共享包

1. **金额格式化**：`formatPrice`/`formatPriceWithSymbol` 在三处定义（admin/utils、admin/PriceDisplay、client/utils）
2. **请求拦截器**：admin/utils/request.ts 与 client/utils/request.ts 实现完全不同，缓存语义相反
3. **订单状态映射**：admin `OrderStatusTag` 与 client `ORDER_STATUS_MAP` 文案略有差异
4. **配送方式映射**：admin 三处定义 + client 一处定义
5. **时间格式化**：两端都直接用 dayjs，但格式模板未抽常量
6. **`DEFAULT_SHOP_ID` 常量**：server 6 处硬编码 + admin 2 处硬编码

**建议**：建立 monorepo `packages/shared` 包，统一导出 `format`、`constants`、`types`，三端引用。

### 5.2 类型不对齐

| 字段 | server | client | admin |
|------|--------|--------|-------|
| `Order.riderId` | `?: string` | `string`（必填） | `string`（必填） |
| `Order.tableNo/address/remark/contactName/contactPhone` | `?: string` | `string` | `string` |
| `MenuItem.spec_groups` | 有 | 无 | 无 |
| `MenuItem.emoji` | 无 | 无（但 menu-manage 表单有） | 无 |
| `Order.statusHistory` | 有 | 无（StatusTimeline 需要但类型无） | 无 |

**建议**：所有实体类型由 server 用 Swagger 生成 OpenAPI schema，client/admin 用 `openapi-typescript` 自动生成。

### 5.3 错误码语义不统一

- server 失败 `code: <http_status>`（200/400/401/500），成功 `code: 0`
- client `RequestError.code`：-1 网络错误、-2 未知错误、其他 = HTTP 状态码
- admin 拦截器按 `responseData.code !== 0` 判断业务失败，但 server 失败 code 永远 ≠ 0，OK；不过业务错误码体系缺失（如 1001=用户不存在）

**建议**：定义业务错误码常量 `BIZ_ERROR_CODES` enum，server filter 中按异常类型映射 code，三端共享。

### 5.4 安全/多租户隔离薄弱

- server AuthGuard 未全局注册，多处 GET 接口公开
- server WebSocket 无 shopId 隔离
- admin ShopManage 页面可越权操作任意店铺
- client 提交订单前端传 price 字段
- server JWT 通过 URL query 传递（OWASP 禁止）

## 七、验证步骤

完成 P0 修复后，建议执行以下验证：

1. **支付链路**：客户端下单 → 调起微信支付 → 支付成功 → 订单状态 paid → 商家接单 → 完成
2. **登录态链路**：token 过期 → 401 → authStore.logout → socket 断开 → 跳登录页 → 重新登录 → 状态恢复
3. **多租户隔离**：A 店铺 admin 登录 → 仅看到 A 店铺订单/菜品/统计 → WebSocket 仅推送 A 店铺事件
4. **订单取消**：admin 后台取消已支付订单 → 订单状态 cancelled + payments 状态 refunded（事务原子）
5. **营销活动**：创建满减促销 → 顾客下单满 X 元 → 自动减 Y 元 → daily_stats 不漂移
6. **运行测试套件**：
   - `cd server && npm test`
   - `cd client && npm test`
   - `cd admin && npm test`
7. **E2E 测试**：`npx playwright test`（已有 admin.spec.ts）
